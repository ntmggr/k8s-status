What these states mean
✓OKHealthy and matching git.
✕DEGRADEDGenuinely broken, needs attention.
!WARNINGThe GitOps controller cannot determine health yet.
↻PROGRESSINGRolling out. Not an error.
≠DRIFTPods healthy, config differs from git.
⊘PRUNEOrphan awaiting cleanup, not an outage.
⏸SUSPENDEDDeliberately paused.
arm64Can only run on arm64 nodes, which on AWS are Graviton.
amd64Can only run on amd64 nodes. No badge means it can run on either.
{{$.Snapshot.AcceleratorBadge}} 2Device requests represented by ready replicas. Not measured device allocation or utilization.
{{$.Snapshot.AcceleratorBadge}} ?Device requests are unknown because it reaches an accelerator through the runtime without declaring it.
{{$.Snapshot.AcceleratorBadge}} unreadyFewer replicas are ready than requested. The scheduling badge, when present, explains a confirmed resource shortage.
{{$.Snapshot.AcceleratorBadge}} target 0No replicas requested. Old pods may still be terminating during a scale-down.
{{icon "warn"}}no cpuThe scheduler cannot place its pods. The chip names what ran out, and an accelerator shortage is coloured apart from cpu or memory.
{{icon "mesh"}}The Policy pill is the cluster-wide default. When AZ_SPREAD is also on, namespace and workload PeerAuthentication overrides are read too: the "permissive" tile and each row's own badge (e.g. "workload override: disabled") show where a service's own effective mode differs from it.
✓STRICT mTLSEvery connection in the mesh must be mTLS-encrypted; plaintext is rejected.
!PERMISSIVE mTLSIstio's own default: accepts both mTLS and plaintext, so an unencrypted connection still gets through.
✕mTLS disabledPlaintext only; nothing in the mesh enforces encryption.
⏸No service mesh detectedIstio is not installed. A legitimate architecture choice, not a fault.
HEALTHThe ring's number is the share of counted services that are OK or progressing right now; the ring itself is that breakdown, healthy slices first. Prune and suspended rows are excluded from the count; drift counts as not healthy. Shows — when nothing is left to count.
az 2Running pods sit in this many availability zones right now.
az 1All running pods sit in one zone: that zone going down takes the whole service with it.
ZONESShare of zone-eligible services that spread across more than one zone right now.
NODESShare of node-eligible services that spread across more than one node right now, tracked independently of zone spread.
IN MESHShare of mesh-eligible services carrying the Istio sidecar on every running pod right now. Sidecar injection only, not a per-service mTLS enforcement guarantee. An Istio ingress gateway reads as "in mesh" too, but that's its own Envoy engine, not an injected sidecar -- gateways are never sidecar-injected by design.
Status is the workload’s health; Sync is whether its manifests match git: two independent things, so PROGRESSING beside Synced is normal. Rows are ordered worst-first. Expand a row to see which components are out of sync. Click a status chip or an at-risk tile to filter the list, and click it again to clear it. A red or yellow stripe on the left edge of a row means DEGRADED or WARNING: the two states worth actually looking at. PROGRESSING and DRIFT get no stripe -- neither needs action right now, though Health counts only PROGRESSING as healthy, since drifted config does not resolve on its own the way a rollout does. {{if $.MultiSource}}
Flux rows show their controller in the Source column. Flux does not compare running manifests against git the way ArgoCD does, so those rows carry no Sync value and never appear as DRIFT or PRUNE.{{end}}
